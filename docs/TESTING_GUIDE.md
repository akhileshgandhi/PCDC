# PCDC — Tester's Guide

This document is for QA testers who are new to the PCDC (Prestige Capability
Development Centre) Case Studio platform. It explains what the product is,
how the pieces fit together, and how to write good test cases against it.

---

## 1. What is PCDC?

PCDC is a case-study-based learning platform for a business school. Faculty
author case studies (a business scenario + questions + a grading rubric),
assign them to sections of students, and students work through a guided,
multi-stage attempt flow that ends in an AI-generated evaluation with a
capability-based score. Admins manage the academic structure (institutions,
departments, courses, batches, sections) and every user account.

There are three portals, each a separate area of the same web app, gated by
login role:

| Portal | Who uses it | URL prefix |
|---|---|---|
| Admin | Program office / platform admins | `/admin/*` |
| Faculty | Teaching staff | `/faculty/*` |
| Student | Enrolled students | `/student/*` |

Logging in with an account routes you straight into the matching portal.
There is no way to see another role's portal without logging out and back
in as a different account — **always confirm which role you're testing as**
before filing a bug, since some pages look superficially similar across
portals but are completely different components.

---

## 2. How the pieces fit together (for context, not required reading)

- **Frontend**: React + TypeScript, talks to the backend over a REST API.
- **Backend**: FastAPI (Python), one router per portal
  (`services/admin`, `services/faculty`, `services/student`,
  `services/simulation` for the case-attempt flow, `services/auth`).
- **Database**: PostgreSQL (Neon).
- **AI**: case evaluation, AI discussion/defense chat, and rubric scoring
  are generated by an LLM call at submission time — this means those steps
  can occasionally be slow (the model is "thinking") and, rarely, fail and
  need a retry. That's expected system behavior, not automatically a bug —
  see §6.

You don't need to read code to test this product, but if a bug report
needs backend confirmation, the relevant files live under `backend/services/`.

## 3. Academic structure (Admin) — the hierarchy everything else hangs off

Admins build a tree that faculty and students are placed into. Test cases
for Admin should walk this hierarchy top-down, since a broken parent breaks
everything under it:

```
Institution
  └─ Department
       └─ Course  (has total_semesters + duration_years — these must agree:
                    total_semesters = duration_years × 2)
            ├─ Batch      (an intake year group, e.g. "2025–2027")
            ├─ Semester   (auto-created when the course is created)
            │    └─ Section   (a class within a semester + batch)
            │         └─ Subject  (per course + semester)
```

Faculty are assigned to institutions/departments (at invite time) and to
specific Sections (to actually teach/see students there). Students are
enrolled into a Course → Batch → Section.

**Good test angles here:**
- Create a course with a duration/semester mismatch (e.g. 2 years, 3
  semesters) — should be rejected with a clear message, not a generic error.
- Create a batch whose year span doesn't match the course's duration —
  same expectation.
- Delete an Institution/Department/Course/Batch/Semester/Section and
  confirm the in-app confirmation dialog appears (not a browser popup) and
  correctly describes what else gets removed/unassigned.
- Use the "Institute" filter on each Academic Setup tab and confirm it
  actually narrows the list to that institute's data only.

|---|---|

| Academic Setup | Institutions / Departments / Courses / Batches / Semesters / Sections / Subjects — full CRUD, Institute filter, in-app delete confirmations. |

| People → Students | Read-only roster (students are created by CSV import or directly in academic setup, not free-form here). |
| People → All Users | Single unified list across all roles, search, role/status filters, Edit, Reset Password, Activate/Deactivate, Delete. Click into a user to see the full profile detail page (profile fields + login history). |
| Teaching Approvals | On/Off toggle for "require approval for faculty self-selection"; Pending/Approved queues. |
| Case Import | Bulk import queue for externally-sourced cases. |

**High-value regression checks** (these were broken and fixed recently —
worth a dedicated test case each):
- **Reset Password** actually delivers a usable set-password link to the
  user's email (previously it silently did nothing).
- **Deactivate / Reactivate** a user, then re-open their profile and
  confirm *none* of their other fields (department, designation, course,
  batch, section, employee ID, etc.) got wiped — a past bug nulled these
  out on every status change.

## 5. The Case Attempt flow — test this end-to-end, every stage

This is the core product loop. **The shipped flow has four stages** — not
six. (An earlier version of this guide listed six based on planning docs
that turned out to be aspirational rather than reflecting what's actually
built; corrected here. If a future build adds the missing stages back, this
section needs updating again.) The app must be able to resume correctly at
any stage after a page reload — that's worth testing explicitly, not just
the happy path straight through.

1. **Reading / Briefing** — case situation is shown before the student
   starts; a countdown timer runs.
2. **Initial Analysis** — free-text answer(s) to the case's structured
   questions, **minimum 200 words** enforced before submit is allowed.
3. **Rapid Fire** — 3 AI-generated questions (personalized per student, based
   on their own Initial Analysis) the student answers in sequence.
4. **Evaluation** — the AI generates the final scored evaluation
   (Capability Breakdown + overall grade) immediately after Rapid Fire is
   submitted.

There is no separate AI Discussion chat, Solution, Defense, or Reflection
screen in the current build, even though some backend/type scaffolding for
them still exists — don't write test cases against stages that aren't
reachable from the UI.

**Specific things to verify:**
- Submitting Initial Analysis with under 200 words is blocked with a clear
  message; at/above 200 words it proceeds.
- Reload the page mid-attempt at each stage — it must resume exactly where
  you left off (not restart, not lose answers).
- Two students who submit **identical answers** to the same case should
  end up with the **same (or near-identical) Capability Breakdown scores**.
  A wide score spread on identical input is a real bug (this was a
  confirmed issue: AI scoring wasn't deterministic — worth a periodic
  regression check with two test accounts submitting the same text).
- The score shown on the Evaluation screen should use **one consistent
  scale** (marks out of the case's total, e.g. "7.9/10") — and the
  **same** number, on the same scale, should appear when a faculty member
  views that same attempt's report. Previously these disagreed (student
  saw out-of-10, faculty saw out-of-100 for the same attempt).
- Capability Breakdown color-coding (green/amber/red per score) must match
  between the student's own view and the faculty's view of the same
  attempt. A score of exactly 75, for example, should be the same color in
  both places.
- If the AI Discussion opening message is slow to generate or briefly
  fails, **submitting Initial Analysis must still succeed** — the analysis
  save is independent of the AI call now. If you ever see "Unable to
  submit your analysis right now," that's a real bug (this exact message
  was a confirmed P1 previously) — check whether the analysis was actually
  saved despite the error (reload and see what stage you're on) before
  filing, since that distinguishes "totally failed" from "saved but
  showed a scary message."

## 6. What's a bug vs. expected AI behavior

Because several steps call an AI model live:
- A few seconds of loading/spinner before AI Discussion, Defense questions,
  or the final Evaluation appear is **normal**, not a bug — file it as a
  performance issue only if it consistently exceeds ~30-60 seconds or the
  UI gives no loading indicator at all.
- Evaluation feedback text will vary in wording between attempts even on
  similar answers — that's expected. The **numeric scores** should not
  swing wildly on identical input (see §5); the **prose** is allowed to.
- If any AI step returns an outright error, the app should show a clear
  message and let you retry, not get stuck. A dead-end with no retry
  option is always a real bug.

## 7. Writing a test case — template

Use this structure so bugs are reproducible and triageable at a glance
(this matches the ticket format already used for this project):

```
Title:        <one-line summary of the behavior being tested>
Module:       <Portal> / <Area>            e.g. Admin / Academic Setup
Severity:     Critical | High | Mid | Low
Priority:     P1 | P2 | P3
Preconditions: <account/role needed, any setup data required>

Steps:
1. Login as <role>.
2. Navigate to <page>.
3. ...

Expected Result: <what should happen>
Actual Result:    <what actually happened — omit while writing a fresh
                   positive test case; fill in only when reporting a bug>
```

**Severity vs. Priority — how to pick:**
- **Severity** = how bad the impact is if it happens (Critical = blocks a
  core flow like login or case submission for everyone; Low = cosmetic).
- **Priority** = how urgently it should be fixed (can be high even for a
  low-severity issue if it's highly visible, e.g. a typo on the login page).

**Good habits:**
- One behavior per test case — don't bundle "check the button works AND
  check the styling AND check the API response" into one ticket.
- Always state which **role** you tested as — Admin/Faculty/Student bugs
  are filed and fixed separately even when the page looks similar.
- For anything score/AI-related, note whether you tried the same input
  more than once, since single-run AI variance is expected (§6).
- When a submit/save action fails, always try **reloading and checking
  whether it actually saved anyway** before writing "does not work" — note
  the outcome either way in the ticket, it changes the diagnosis a lot.
